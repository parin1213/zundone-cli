# zundone-cli — agent guide

A small Node CLI that speaks text via a [VOICEVOX](https://voicevox.hiroshiba.jp/) engine. It supports two backends — `docker` (auto-launches a containerized engine) and `http` (talks to a pre-existing engine URL) — and plays the resulting WAV using whatever audio command the host OS has.

The package is published as [`zundone-cli`](https://www.npmjs.com/package/zundone-cli) on npm. The binary names are `zundone` and `zd`.

## Quick commands

```bash
pnpm dev -- "done"   # tsx src/cli.ts "done"
pnpm test            # vitest run         (must pass on Ubuntu CI)
pnpm typecheck       # tsc --noEmit
pnpm build           # tsup → dist/cli.js
```

> The `--` separator on `pnpm dev` is needed so pnpm passes the literal text through to `tsx`.

## Layout

- `src/` — TypeScript source. Edit here.
- `dist/` — generated by `tsup`. Gitignored.
- `test/` — vitest tests. Runs on Ubuntu in CI.
- `cac` is the argv parser; commands and options are declared in `src/`.

## Testing notes

- Tests must run on Ubuntu (GitHub Actions). **Never hardcode Windows paths** in test fixtures or `spawn` cwds.
- Tests must not require a live VOICEVOX engine, Docker daemon, or audio device. If you add an integration-style test, gate it behind an env var or skip on CI.
- Audio playback is host-dependent and must not be invoked from tests.

## Configuration namespaces

Part of the public API. Don't rename without bumping a major:

- Backend: `ZUNDONE_BACKEND=docker|http`
- Engine URL: `VOICEVOX_URL` (defaults to `http://127.0.0.1:$ZUNDONE_DOCKER_PORT`, or `:50021` if unset)
- Docker tuning: `ZUNDONE_DOCKER_CONTAINER`, `ZUNDONE_DOCKER_IMAGE`, `ZUNDONE_DOCKER_PORT`
- Player tuning: `ZUNDONE_PLAYER`, `ZUNDONE_PLAYER_ARGS`
- Cache dir: `env-paths("zundone")` (so e.g. `~/.cache/zundone` on Linux)
- Cache toggles: `ZUNDONE_CACHE_DIR`, `ZUNDONE_NO_CACHE`

## Release flow

We use [release-please](https://github.com/googleapis/release-please) on `main`. **Don't manually edit `package.json` version, don't manually `git tag`.**

### How releases happen

1. Merge a PR with a [Conventional Commits](https://www.conventionalcommits.org/) message (`feat:`, `fix:`, `feat!:`, etc.) into `main`.
2. `.github/workflows/release.yml` runs release-please-action.
3. release-please opens (or updates) a PR titled `chore(main): release zundone-cli X.Y.Z` with the version bump + `CHANGELOG.md`.
4. Merging that PR tags `vX.Y.Z`, creates a GitHub Release, and the same workflow publishes to npm via OIDC (Trusted Publisher — no token, with provenance).

### Conventional commits cheat sheet

| Prefix       | Effect       | Example                                   |
| ------------ | ------------ | ----------------------------------------- |
| `feat:`      | minor bump   | `feat: add SAPI fallback player`          |
| `fix:`       | patch bump   | `fix: docker port mismatch on macOS`      |
| `feat!:` / `BREAKING CHANGE:` | major bump | `feat!: rename ZUNDONE_BACKEND values` |
| `chore:` / `docs:` / `refactor:` / `test:` / `ci:` | no bump | `chore: deps update` |

Set the **PR title** to the conventional commit message — squash-merge uses the title verbatim, which is what release-please reads.

### Baseline

`release-please-config.json` pins `bootstrap-sha` to the `v0.1.0` baseline. `.release-please-manifest.json` tracks the current released version. release-please updates it; don't edit by hand.

## Branch protection

- `main` requires PR (squash merge only, linear history)
- `test` job in `.github/workflows/ci.yml` must pass
- No force push, no deletion
- Admin (you) can bypass — but don't, except for plumbing emergencies

## Local quirks

- Windows users: line-ending warnings (`LF will be replaced by CRLF`) are noise and safe.
- `.envrc` is gitignored. It's used to hold an npm bootstrap token; keep it out of commits.
- `pnpm-lock.yaml` is committed. CI runs `pnpm install --frozen-lockfile`.
